# RoboTwin: Dual-Arm Robot Benchmark with Generative Digital Twins Note

## Navigation
- Paper card: [RoboTwin: Dual-Arm Robot Benchmark with Generative Digital Twins card](../cards/RoboTwin.md)

## Reading Notes



### Introduction

**目的：**生成多样化的专家数据集，并为双臂机器人任务提供一个与真实世界相符的评估平台



**目前方法以及局限**：

- 遥操作：能够产生高质量的演示数据，但通常成本高昂、耗时费力，并且难以涵盖机器人在实际部署中遇到的各种场景
- 仿真中的算法轨迹生成器：这类算法根据仿真器里的状态信息、任务规则和手写启发式，自动算出机器人应该怎么动
  - 依赖特权信息：策略在训练数据中学到的是“完美世界里的动作分布”，而部署时面对的是不确定感知下的状态分布。且这种方法掩盖感知和决策难点
  - 每个任务单独写规则，即每个任务都需要人工写一套任务脚本、关键位姿、抓取逻辑、动作顺序或规划约束
    - 开发成本高，扩展慢
    - 规则通常只覆盖有限场景（规则的假设过多）
    - 任务之间难以复用，抓杯子的规则不能直接用于抓剪刀
    - 组合任务和双臂任务尤其困难
- 能够利用有限的人类演示数据生成大规模的模拟专家数据（类似GR00T的做法）：难以处理超出预定义配置的任务变体，从而限制了它们在新场景中的通用性（比如“拿杯子放到柜台上”可以扩增为不同杯子位置、不同柜台位置、不同厨房布局；但如果任务变成“打开冰箱、判断里面有什么、取出指定食材、关门”，原来的片段可能就不够用了）



能做到：

- 任务生成；
- expert trajectory 生成；
- 域随机化；
- policy 训练数据；
- 标准化评测协议；
- 一定程度的 sim-to-real 对齐。



**主要贡献：**

- 我们建立了一个便捷的实物到仿真转换流程，该流程仅需一张来自真实世界的RGB图像，即可生成目标物体的多种3D模型，这得益于我们开发的3D生成式基础模型
- 我们创建了一个空间感知代码生成框架，该框架利用大型语言模型和目标物体的空间标注信息，自动生成专家级演示数据
- 我们开发了一个双臂操作任务的标准基准测试，该测试包含真实世界的远程操作数据以及针对相应场景生成的高保真合成数据



### Method

看下来感觉非常工程，有相当多工程化细节

#### Generation of Diverse Digital Assets

1. 从单张图片到多样化描述 

   - **输入：** 拍摄一张现实世界物体的 2D RGB 照片。

   - **处理：** 使用 **GPT-4V** 分析图像生成原始描述。

   - **多样化：** 利用语言模型自动修改这些描述，产生一系列“相似但视觉特征不同”的物体描述（例如改变颜色、材质或局部细节）。

2. 生成多样的 2D 图像
   - **处理：** 将多样化的描述输入 **SDXL-Turbo**（稳定扩散模型），生成大量代表同一类物体、但外观各异的新 2D 图像。

3. 构建 3D 模型 

   - **工具：** 使用 Deemos 的 **Rodin 平台**。

   - **输出：** 将上述 2D 图像转化为完整的 3D 模型，包括详细的几何结构（Geometry）、表面法线（Normals）、线框图（Wireframes）和纹理（Textures）。

4. 质量校验与物理仿真设置

   - 双重验证：
     - **定量：** 使用 UCLIP-I 指标计算相似度。（计算的是2D图片和3D资产之间的相似度）
     - **定性：** 再次使用 GPT-4V 进行视觉验证。质量不合格的资产会被自动剔除并重新生成。

   - **物理属性：** 利用 GPT-4V 识别物体材质，并分配物理参数（如摩擦力、质量等）。为了增加鲁棒性，系统会在这些参数上加入 $\pm 5\%$ 的随机波动。



####  Spatial Annotation Framework for 3D Assets

这一部分主要说如何给3D资产做标注，方便后续LLM生成机器人任务代码

框架定义了一套标准化的空间几何描述体系：

- 关键点 (Key Points)
  - **功能点 (Point for Function)**：工具发挥作用的核心位置（如锤子的敲击面）。
  - **接触点 (Point for Contact)**：机器人抓握的位置（如手柄中心）。
- 主轴 (Axes)
  - **功能轴 (Function Axis)**：执行任务的方向（如敲击的方向向量）。
  - **接近轴 (Approach Axis)**：工具靠近目标的方向，用于规划入场轨迹。
  - **侧向轴 (Lateral Axis)**：垂直于前两轴，用于锁定物体的 3D 旋转姿态。



标注方法——半自动迁移机制：同一类别的不同 3D 模型不需要逐个重新标注。先在一个源图像/源模型上标点，再用 Stable Diffusion encoder 的 diffusion features 做特征点匹配，把关键点迁移到同类目标模型上



主要创新点是提出了function axis这一个标注





#### Expert Data Generation

如何把空间标注转化为可执行的机器人专家轨迹



1. **Scene Initialization**：初始化任务场景，包括物体、初始位姿和环境配置。比如 hammering task 中，需要先放置 hammer 和目标物体。

2. **Task Decomposition**：LLM 根据人类输入的任务描述，把复杂任务拆成子任务。 例如 “hammer a nail” 可以拆成：
   1. 抓取锤子；
   2. 把锤子移动到钉子上方；
   3. 敲击钉子；
   4. 把锤子放回原位。

3. **Constraint Inference**：LLM 对每个子任务推断空间和时间约束。这里会用到 3.2 节的标注：

| 子任务类型 | 使用的标注                                  | 约束含义                                       |
| ---------- | ------------------------------------------- | ---------------------------------------------- |
| 抓取类任务 | contact point、approach axis                | 末端执行器应对准抓取点，并沿合适方向接近       |
| 操作类任务 | function point、function axis、目标物体位置 | 工具功能点要对齐目标点，功能方向要满足任务要求 |

例如 hammering 中，锤头的 function point 需要对齐钉子，锤子的方向也要适合敲击。

4. **Robot Behavior Generation**：LLM 根据推断出的空间约束调用 API 生成行为代码。系统会在世界坐标系下计算 object functional point、contact point、target point 和 end-effector pose。抓取时主要依赖 contact point 和机器人运动学限制；复杂工具操作时，则通过对齐工具 functional point 与目标点，并满足方向约束来计算目标姿态。

5. Success Evaluation：执行完成后，系统检查任务是否成功。比如 hammering task 中，可以检查钉子是否被敲到目标深度。

6. Iterative Refinement：如果失败，系统会收集错误信息，包括 runtime error、trajectory planning failure、最终物体状态与目标状态的偏差等。然后把这些信息连同原始任务描述、物体标注、上一版代码一起反馈给 LLM，让 LLM 重新生成或修改代码，直到达到预期效果。





第三步LLM会依照prompt调用作者设计的高层api，示例：

```python
# 获取位姿
get_grasp_pose_to_grasp_object(...) 
get_grasp_pose_from_goal_point_and_direction(...) 
get_actor_functional_pose(...) 
get_avoid_collision_pose(...)

# 左/右臂移动
left_move_to_pose_with_screw(pose) 
right_move_to_pose_with_screw(pose) 
together_move_to_pose_with_screw(left_target_pose, right_target_pose) 
```
