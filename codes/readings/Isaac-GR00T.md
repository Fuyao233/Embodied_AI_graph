# Isaac-GR00T



## 真机部署指南

这是一份 **GR00T 真实机器人部署指南**，覆盖从硬件准备、数据采集、模型微调，到真实机器人闭环控制与问题排查的完整 VLA（视觉—语言—动作）落地流程。整体链路为：硬件准备 → 数据采集 → 数据清洗与格式转换 → 模型训练 → 开环验证 → ZMQ 部署 → 闭环测试 → 抖动与停顿优化。

### 1. 硬件与传感器

机器人需要支持实时关节状态反馈、稳定控制接口和约 **30 FPS 的动作执行**。推荐使用腕部相机、第三人称相机和机器人本体状态作为多模态输入。

需要注意：30 FPS 指相机采集和机器人动作执行频率，不代表模型必须以 30 Hz 推理。模型可通过一次输出多步动作块，并结合异步推理，以约 10 Hz 推理支持 30 FPS 执行。

遥操作设备的选择主要取决于成本、机器人构型依赖和操作直觉：

- 键盘、手柄、SpaceMouse：成本低，适合快速起步。
- 主从机械臂：操作直观，但依赖相似的运动学结构。
- UMI、Fast-UMI：跨机器人适配能力较强，适合通用 VLA 数据采集。
- VR、动作捕捉、外骨骼：灵活或直观，但集成和硬件成本更高。

### 2. 数据采集

数据质量是部署效果的核心。主要要求包括：

- 两路相机 FPS 严格匹配，并尽量同步触发。
- 关节状态采样频率应高于相机帧率。
- 完整记录时间戳，便于后续对齐。
- 同构机器人优先记录关节空间数据；跨构型采集与部署时，优先记录末端执行器位姿。
- 初期应保持相机位置、光照、物体位置和机器人初始姿态稳定，先验证有限场景，再逐步扩大数据分布。

### 3. 数据预处理

数据清洗分为两层：

1. **脚本过滤**：检查相机延迟、双相机时间差及机器人状态异常跳变。
2. **人工复核**：删除图像模糊、图像与动作不同步、任务失败、路径冗余或动作不连续的轨迹。

之后需要进行时间戳对齐、删除轨迹首尾的空闲片段，并将过长轨迹拆分为多个子任务，最终转换为 GR00T 兼容的 **LeRobot 格式**。

### 4. 模型训练建议

针对单任务微调：

- 最少准备约 **100 条有效轨迹**；极窄任务可能约 30 条即可起步。
- 推荐收集 **200 条以上**，效果通常更稳定。
- 操作任务采集频率建议为 20–50 Hz。
- 默认使用 **State-relative Action Prediction（状态相对动作预测）**，比绝对动作更容易收敛，并能提高动作块之间的一致性。
- 默认 Action Chunk 长度为 16；若使用 RTC，至少提高到 32。
- Batch Size 应在显存允许范围内尽量增大。
- 微调可从单张 40 GB 以上显存的 GPU 起步，8 张 H100/H20 属于生产级配置，不是最低要求。

训练完成后先做开环评估，确认模型收敛和输出质量，但最终效果必须通过真实机器人的闭环测试验证。

### 5. 部署架构

文档提供两种推理方式：

- `Gr00tPolicy` 直接运行：适合模型和机器人控制位于同一台机器。
- **ZMQ Server-Client**：推荐用于真实部署，将 GPU 推理服务器与机器人本地控制解耦。

机器人侧主循环包括：采集双相机图像和机器人状态、组织 observation、向模型服务器请求 Action Chunk、轨迹平滑与安全检查、按约 30 FPS 执行动作。

安全层面应加入：

- 关节角度和末端位姿软限制。
- 超出工作空间时立即停止。
- 软件快捷键或物理急停。
- 动作插值和平滑处理。
- 使用 JPG 等压缩图像降低网络传输带宽。

### 6. 抖动问题

抖动可能来自三类原因：

- **动作块内部抖动**：通常说明模型训练不足或数据质量差，应增加数据、延长训练并检查训练与验证环境一致性。
- **动作块边界抖动**：相邻 Action Chunk 输出不一致，应采用状态相对动作预测及 RTC。
- **模型轨迹平滑但机器人仍抖动**：大概率是驱动、插值算法、低层控制或硬件问题。

建议保存所有 Action Chunk，并将关节输出通过正向运动学转换为末端轨迹进行三维可视化。

文档还提出三项量化指标：

- 动作块内部平均加速度幅值。
- 动作块边界的位置跳变量。
- 动作块边界速度方向的余弦相似度。

### 7. Stop-and-Go 停顿问题

停顿的根本原因是同步闭环中，数据采集、网络传输、模型推理和后处理的总延迟超过控制周期。30 FPS 对应约 **33 ms** 的时间预算，而 VLA 系统通常难以满足这一限制。

两类解决方案：

- 优化推理链路：压缩数据、边缘推理、模型量化或使用更小模型。
- 使用调度算法：异步推理、滚动时域、时间集成和 RTC。

文档最推荐 **异步推理 + RTC**：

- 后台线程持续采集观测并推理。
- 主线程持续执行当前动作块。
- 新旧动作块在重叠区域进行平滑融合。
- Action Chunk 长度至少为 32。

但目前 GR00T 中 RTC 仍属于实验性底层能力，尚未完整接入 `Gr00tPolicy` 和 ZMQ Server-Client，需要开发者手动集成，且缺乏现成测试与完整示例。

## 核心结论

该指南的重点不是单纯“训练出一个模型”，而是构建一条稳定的工程链路。成功部署依赖四个关键因素：

1. 高质量、严格同步的数据。
2. 状态相对动作预测和足够长的 Action Chunk。
3. 推理服务与机器人控制解耦。
4. 通过异步推理、RTC、轨迹平滑和安全限制解决实时性与动作连续性问题。
